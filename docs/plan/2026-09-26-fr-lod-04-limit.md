## 2. The work

### L0. Baseline objects, before any engine edit

Build the engine at `ccbbaf1` into `build/base` on MinGW (all three
backends) and into a guest-local directory in WSL (`ONFPLAT=x86l`), and keep
every `.o`. D-569 expects every non-MVS object to be byte-identical after the
change; that is proved against this baseline, not assumed. Also keep
`gcc -E -P` of `onflyeng.c` under `-undef -D__MVS__ -DONF_FP_SOFT2C`, so the
MVS preprocessed text can be compared too.

### L1. Tests first, shown failing

1. `tests/run_plim.py` (new, run by the `eng` target with `$(CC)`):
   preprocesses `onfplat.h` under `-undef` with each platform's macros
   (`__MVS__`, `JCC`, `__s390x__`, `_WIN32`, `__linux__ __x86_64__`, none)
   and asserts `ONF_MEMLIM` is D-568's value for each, and that `-DONF_MEMLIM=n`
   overrides it. If Q2 below is answered "fix", it asserts the same for
   `ONF_MAXPAY`. It proves the header's logic under gcc's preprocessor; it
   does not prove what JCC or GCCMVS do with it.
2. `tests/run_eng.py`: the TE-08 replay stops skipping. It takes, per
   backend, two more executables built with `-DONF_MEMLIM=64` and
   `-DONF_MEMLIM=1048576`, and replays each of `run_dec.py`'s TE-08 cases
   through the executable built at that case's limit: ONF105E with return
   code 12 for "exceeds", ONF003I with 0 for "within". A missing variant is a
   FAIL, not a skip. One more check exercises D-568 on the shipped build: a
   network whose header counts demand more than 8,388,608 B still verifies
   (ONF003I, 0), because the non-MVS limit is 0.
3. `Makefile` `eng`: builds the two variants per backend by compiling
   `onflyeng.c` once more with each `-DONF_MEMLIM` and linking the same
   objects, as the `-DONF_NOREQ` variant is built (D-228), and passes them to
   `run_eng.py`; runs `run_plim.py`.
4. One helper builds the over-limit network, the synthetic `good` network
   with its edge count raised so the requirement exceeds 8,388,608 B and its
   header CRC repaired. `run_eng.py` and the MVS job of L4 both use it, so the
   file MVS refuses is the file x86 admits.

Run `mingw32-make eng` against the unchanged engine and show the failures:
`run_plim` finds no `ONF_MEMLIM`, and "TE-08 exceeds memory limit" reports
ONF003I where ONF105E is wanted, because `onflyeng.c` ignores the macro.

### L2. The change

1. `engine/include/onfplat.h`: `ONF_MEMLIM`, inside `#ifndef ONF_MEMLIM`,
   8388608L where the platform is MVS 3.8j and `0` elsewhere, the MVS test
   written in the same order as `ONF_PLATID`'s chain so that JCC is matched
   after `__s390x__` and `_WIN32` (D-291). `0` is spelled exactly as the
   literal it replaces, so the preprocessed `onflyeng.c` is unchanged where
   the limit is 0.
2. `engine/src/onflyeng.c`: pass `ONF_MEMLIM` to `onfdec`; the stale comment
   is rewritten to cite D-116, D-567 and D-568. `ONF_ENGVER` per Q3.

*Note 2026-09-26, after D-572 and D-573.* `ONF_MAXPAY` moves onto the same
MVS test as `ONF_MEMLIM` (D-572), so `run_plim.py` asserts both macros, and
JCC's value becomes 67108864L. `ONF_ENGVER` becomes "0.5.1" (D-573).
3. `tests/run_eng.py` and `tools/onfres.py`: the stale comment and the
   `eng/TE-08` exemption go. The strict closing line becomes
   `28 PASS, 0 SKIP, 0 PENDING, 5 EXEMPT`.
4. `REPLICATING.md`: five exempt checks, the TE-08 clause removed.

*Note 2026-09-26, after D-573.* With `ONF_ENGVER` at "0.5.1", every
ONFLYENG object carries a changed version string, so "byte-identical" above
becomes: every object other than ONFLYENG's own is byte-identical to L0, and
each ONFLYENG object (the shipped build and the `-DONF_NOREQ` variant, per
backend) differs from L0 in exactly one byte, `0` (0x30) to `1` (0x31),
inside the version string. The MVS preprocessed text differs in two places:
the version string and `onfdec`'s third argument.

### L4. TK5 under GCCMVS

1. Start TK5 detached (`Start-Process ... mvs.bat`); the tools set codepage
   819/1047.
2. `python tools/mvsrun.py --run`, then `--compare` against the x86-64
   recording: the five `srext` fingerprints of Section 8.4 from the changed

3. `python tools/mvsrun.py --te08` (new, with a lab-free deck test in

   thirteen units, then runs the GO step with `PARM='VERIFY'` over L1's

   over the installed `srext` dataset (D-286), must end `ONF003I` at
   `COND CODE 0000`. This is TE-08 through the shipped GCCMVS ONFLYENG.
4. Shut down with `script scripts/shutdown` once no job runs.

## 6. What this plan will NOT prove or change

- Rows 4 and 5 (Linux s390x) and row 7 (JCC) are not re-run (D-570).
  `ONF_MEMLIM`'s JCC value is proved only by the x86 preprocessor.
- Row 6's `path` half is not re-run.
- 8M is what a TK5 job may ask for, not what ONFLYENG can obtain (D-116
  notes a compile hitting `S878` far below it). A network whose requirement
  is just under 8M may still fail at allocation; no such network is run.
- The CICS adapter keeps a limit of 0 (S9).
- Every MVS result is under Hercules, not IBM Z hardware (VL-01, VL-139).
