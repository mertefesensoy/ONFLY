## 1. Problem / motivation

Appendix A.2 holds design decisions the architect proposed while writing the
specification. They are listed separately from A.1 so that a proposal is never
mistaken for an owner decision, and the protocol is explicit that one is never
promoted on silence. Thirty-four proposals have been raised; thirty are struck.

Four are not, and they have been carried unresolved since before Phase G:

| ID | What it asks | Cost of leaving it |
|---|---|---|
| P-08 | Add an x86-64 / SOFT2C row to the Section 8.3 determinism matrix | ACC-5 does not count a combination `make test` has run on every build since D-220, and MVS rows 6 and 7, both SOFT2C, have no same-library comparand on another platform |
| P-11 | Fix *whose* standard error ACC-4's shape clause means | A requirement whose verdict depends on an unstated reading |
| P-12 | Annotate Section 9.2's Phase A row so G0 reads as closed | None; see Section 3 |
| P-13 | Correct `data/networks/MANIFEST.json`'s `srext.acceptance.not_proven` | **A false statement on disk about the shipped network** |

P-13 is the one that matters. The other three are tidiness; P-13 is a record
that a reviewer reads *instead of* the SRS, and it is wrong.

P-01 to P-06 are also unstruck, but they are a different kind of item: each
describes a design that the specification has since absorbed into a numbered
requirement (NR-12, NR-08, NR-13, IR-COM-05, ACC-3's floors). They are not in
this session's scope and are named here so that "the backlog is cleared" is
read as the four items above, not as all ten.

### 2.1 P-13 is worse than P-13 says

The field at `prep/extract.py:2191` reads:

> Every result is x86-64. Nothing is proven for Linux s390x, MVS 3.8j or
> z/OS; the v1.1 header has never been decoded by GCCMVS. ACC-4 fails

P-13 names three false clauses. There are **five**:

|---|---|---|

| "Nothing is proven for Linux s390x" | **False** | D-234, VL-82 |

that step re-derives the subcircuit, so re-running it rewrites
`data/networks/onfnet-malecns-v1.0-srext.bin` and any differing byte
invalidates every Section 8.4 fingerprint and every MVS result taken against
them.

### 2.2 P-08's combination already runs

`make golden` builds three binaries from the same `tests/tstgld.c`:
`tstgld_soft.exe` (SOFT3E), `tstgld_nat.exe` (NATIVE) and `tstgld_2c.exe`
(`$(C2CFLAGS) $(SF2CFLAGS)`, SOFT2C). It runs `tests/run_gld.py` on each and
then compares all three with `tools/cmpgld.py`. `make test` depends on
`golden`. So the row P-08 asks for has been evidenced on every build since
D-220; it simply has no line in Section 8.3, so ACC-5 does not formally count
it.

The owner declined writing the row on that standing fact alone (D-447). The
row is written from a measurement taken in this session or not at all.

### 2.3 P-11 is not load-bearing today

`prep/acc4.py` compares each successive drop against
`a_["onfly_se_hz"]`, ONFLY's own standard error at the **earlier** rate.
Evaluated on `data/calibration/acc4.json`, every transition is an increase:

```
  10->40 drop=-10.6833  SE_earlier=0.7714 (ok)  SE_later=1.5425 (ok)
  40->60 drop=-14.0333  SE_earlier=1.5425 (ok)  SE_later=1.4329 (ok)
  60->120 drop=-40.0000  SE_earlier=1.4329 (ok)  SE_later=1.4961 (ok)
 120->200 drop=-20.4167  SE_earlier=1.4961 (ok)  SE_later=0.9253 (ok)
```

The clause passes under every candidate reading. Adopting P-11 moves no
verdict; it fixes the ambiguity while nothing depends on the answer.

## 4. What this will NOT prove

Fixed here, before the work, so that the closing report cannot grow claims.

1. **Platform.** Everything measured in this session is **x86-64 Windows 11,
   mingw32 gcc, Python 3.13**. No result here is a Linux s390x, MVS 3.8j or
   z/OS result.
2. **The new determinism row is an x86 row.** It adds no MVS or z/OS
   coverage. ACC-5 row 7's `path` half stays at 5 of 19 golden requests and
   row 8 (z/OS) stays empty.
3. **P-11 proves nothing new about ACC-4.** It removes an ambiguity. The
   verdict, the seeds, the reference and the magnitude deviations at 10 and
   40 Hz are all exactly as VL-112 recorded them.
4. **The manifest correction is a documentation correction.** It restates
   VL-82, VL-91, VL-93, VL-95, VL-96, VL-102, VL-104, VL-106 and VL-112,
   every one of which was measured in an **earlier** session. Nothing in
   slice 4 re-measures any of them, and the corrected note is only as true as
   those records are.
5. **Phase F is untouched** and TBD-13 (a source of a real CICS) stays open.
6. **VL-01 still applies.** Hercules and QEMU are emulators; nothing here
   changes that, and nothing here runs on real hardware.
