## 1. Problem / motivation

ACC-5 is satisfied only when every golden-suite request yields the same
fingerprint on every combination Section 8.3 lists. Row 7, the TK5 / SOFT2C /
**JCC** row, was filled on 2026-09-15 by D-281…D-286 and VL-93, but only for
`srext`: five of the nineteen Section 8.4 requests. G-01 to G-14, the whole
`path` half, have no JCC counterpart.

That gap is not cosmetic. Row 7 exists to answer one question that no other
row can: **is a fingerprint a property of ONFLY's source, or of one code
generator?** Everything the engine does is integer work over a software float
library, so a code-generation difference would not surface as a rounding
difference; it would surface as a wrong answer, or not at all. Rows 6 and 7
are the only pair that can distinguish those. Today that pair covers five
requests on a 501-neuron network, and in particular it covers **none of the
three rejection paths**: G-11 (ONF201W, reserved stimulus), G-12 (ONF203E,
unknown stimulus) and G-13 (ONF202E, out-of-range rate) are `path` requests.
Row 6 reached them on 2026-09-15 and called it "the first time the MVS engine
has reached FR-BAT-05's, D-41's and FR-SIM-06's rejection paths". Under JCC
they have never been reached at all.

D-444 offered this work as an alternative on 2026-09-17 and the A.2 backlog
was taken instead. That backlog is now cleared, every phase through G is
COMPLETE, and Phase F cannot start until the IBM Z access request is granted. This is
the largest named coverage gap left that the engineer can actually close.

## 2. What the evidence already says, and what it costs

### 2.1 The tool is nearly ready and refuses on purpose

`tools/mvsjcc.py` is already network-generic almost everywhere: `run_deck()`
reads `mvsrun.NET_DSN` and `mvsrun.REQ_DSN`, `process_run()` writes
`rsp-<net>-2c.bin`, and `run_compare()` resolves the golden file through
`mvsrun.golden_fingerprints()`, which takes its network at call time. The one
thing standing in the way is deliberate: `main()` refuses `--net` outright:

    Row 7 is `srext` only, and this file takes no --net. Saying so
    ... the wrong network under the right job name.

That refusal guards a real failure mode, and `tools/mvsrun.py` records the
same class of bug biting twice in one session through mutable-looking
defaults (`write_cards`, `golden_fingerprints`). The plan below does not
delete the guard; it replaces "refuse the network" with "make the job name
and the response dataset *follow* the network, and assert that they agree."

### 2.2 The cost, measured, with a spread nobody has reported

Row 6 ran these same fourteen requests under GCCMVS. It ran them **twice**,
and the two runs are the honest cost estimate:

| Run | Job | Wall | `GO` step CPU |
|---|---|---|---|
| The run VL-91 reports (`ee7949b`) | JOB 279 | 05:57:26 → 07:01:11, 63 min | **63 min 04.79 s** |
| The listing that ships today (`891de23`) | JOB 308 | 14:15:46 → 16:59:38, 2 h 44 min | **157 min 52.69 s** |

Same job, same engine, same fourteen requests, **2.5x apart**, and the second
shared the host, as `$HASP308 ONFPRUN ESTIMATED TIME EXCEEDED BY 30 MINUTES`
on the cancelled JOB 304 says in the handover doc. `rsp-path-2c.bin` is
byte-identical across the two, which is a reproducibility datum in its own
right: only the clock moved.

JCC's generated code is slightly **faster** than GCCMVS's on the same work:
`srext`'s `GO` step cost **15 min 29.88 s** under JCC against **17 min
43.33 s** under GCCMVS, a factor of 0.874. Applying that to the range above:

> **Estimate: the `GO` step will cost 55 min of CPU on a quiet host and up to
> 2 h 18 min on a contended one**, plus thirteen JCC compiles, a PRELINK and
> a link. The whole job is expected to take **1 to 3 hours of wall time.**

This estimate is stated *before* the run, with its spread, because slice 1 of
Phase E gave the owner "47 minutes" for the row 6 `path` run and was wrong by
a third, for a reason (edge density) that was knowable in advance.

`tools/mvsjcc.py` currently collects with `timeout=7200`, which is two hours. On a
contended host that expires **while the job is still running**, and the
listing would be lost. It has to rise.

## 3. The plan, in five slices

Each slice ends with something shown. Slices 1 and 3 are the only ones that
touch TK5.

### Slice 1: bring the lab up and take stock

    C:\hercules-lab\mvs-tk5\mvs.bat          (D-459 authorises this)

Then, before anything is submitted:

* the Hercules console answers on `127.0.0.1:8038`;
* **the codepage is set to `819/1047`.** VL-87 records that it had reset to
  `default` before the first submission of the G0 session, and VL-18 records
  that the pin is load-bearing and lives outside the repository. A run
  started on the wrong codepage is a corrupted run, not a failed one;
* `USER.ONFLY.PNET` and `USER.ONFLY.PREQ` are catalogued and readable. Both
  were created on 2026-09-15 for row 6 and TK5's DASD persists, but *"it
  should still be there"* is not a measurement. One IDCAMS `LISTCAT` job
  answers it. If either is gone, `tools/mvsrun.py --net path --install-net`
  and `--net path --req` rebuild them by their existing, already-verified
  paths, with no new code.

### Slice 2: make `tools/mvsjcc.py` network-aware (x86 only, no lab)

1. `main()` accepts `--net {srext,path}` and calls `mvsrun.select()`, in place
   of the blanket refusal. The refusal's *reason* is preserved as a check, not
   deleted.
2. A per-network name table in `tools/mvsjcc.py`, because row 7's names belong to
   row 7's driver, not to `mvsrun.NETS`, which documents row 6's jobs:

   | Network | Job | Response dataset |
   |---|---|---|
   | `srext` | `ONFJRUN` | `USER.ONFLY.JRSP` |
   | `path` | `ONFJPRUN` | `USER.ONFLY.JPRSP` |

   `srext` keeps the names VL-93 recorded, so that entry stays true and the
   printer and punch trail stays unambiguous about which row produced what.
3. `run_deck()` asserts that the job name, the response DSN and
   `mvsrun.NETNAME` agree before a single card is submitted. This is the
   guard the refusal was standing in for, expressed as an assertion.
4. The `--run` collect timeout rises from 7200 s to **14400 s** (4 hours), on
   §2.2's measured spread.
5. `tests/test_mvsjcc.py`: builds the deck for both networks with no lab
   present and asserts each one names its own job, its own response dataset
   and its own network DSN, that the link order still equals
   `mvsrun.UNIT_MEMBERS`, and that selecting `path` never leaves an `srext`
   name behind. It joins the Makefile's `prep` target so `make test` runs it.

   > **AMENDED 2026-09-18 by D-464.** This item was false on disk when it was
   > drafted. `tests/run_mvsjcc.py` already exists, its stated purpose is
   > "Everything about ACC-5 row 7 that can be judged without TK5", and it

### Slice 4: judge it

    python tools/mvsjcc.py --net path --compare data/phase-e/jcc data/phase-d/x86w

MVS defect cannot make rows 6 and 7 agree with each other.

## 4. What this will NOT prove, stated in advance

* **SOFT2C only.** JCC has no TT-01 or TT-02 result, so VL-03's caveat stands
  for the float library's own conformance under JCC. What row 7 shows is that
  the *engine* agrees, not that JCC's SoftFloat is IEEE-conformant.
* **Row 8 stays empty.** This is not Phase F and does not start it.
* **Hercules is an emulator**, so VL-01's argument applies unchanged.
* **A pass is one run.** Row 6's own two runs show the bytes reproduce and
  the clock does not; a single JCC run says nothing about its own repeatability.
* **Nothing here touches ACC-1, ACC-2, ACC-3, ACC-4, ACC-6 or ACC-7**, which
  remain exactly as Phase E left them.

## 5. Risks

| Risk | Likelihood | What happens | Mitigation |
|---|---|---|---|
| `USER.ONFLY.PNET` or `PREQ` gone | Low | The run ends at ONF108E or with no requests | Slice 1 measures it; existing tools rebuild |
| The job outruns the collect timeout | Medium on a contended host | The listing is lost and the CPU is spent | Timeout raised to 4 h in slice 2 |
| JCC cannot handle the larger network | Low | Storage abend in `GO` | `path` is 951,200 bytes against `srext`'s 171,768; row 6 ran it in `VIRT 2624K` against an 8M region (D-116). JCC's `srext` run used `VIRT 964K` against GCCMVS's 1040K, so JCC is not the hungrier of the two |
| A fingerprint disagrees | Low | ACC-5 row 7 FAILS for `path` | **This is a result, not an accident.** It would be reported as a finding against the source-versus-code-generator question row 7 exists to ask, and escalated to the owner, not worked around |
