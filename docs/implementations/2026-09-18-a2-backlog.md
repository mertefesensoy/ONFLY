## 1. Problem and motivation

Appendix A.2 holds proposals the architect raised while writing the
specification. They sit apart from A.1 so a proposal is never mistaken for an
owner decision, and the protocol forbids promoting one on silence. Four had
gone unresolved since before Phase G, which closed the day before this session
(D-442). With the dependency order A, B, C, D, E, **G**, F, H now carrying no
open phase before F, and F blocked on the IBM Z access request, which has not been
granted, the backlog was what remained that could be **finished** rather than
started.

Three of the four were tidiness. One was not.

**`data/networks/MANIFEST.json` carried a false statement about the shipped
network.** The `srext.acceptance.not_proven` field is the paragraph a reviewer
reads *instead of* the SRS when asking what the MVP network has and has not
been shown to do. P-13 reported it false in three places. Checked against the
record, it was false in **five**, and P-13's own reasoning was stale as well.

| Clause | Status | Evidence |
|---|---|---|
| "Every result is x86-64" | False | Phase D ran all four networks on Linux s390x (D-234) |
| "Nothing is proven for Linux s390x" | False | D-234, VL-82 |
| "...or MVS 3.8j" | False | D-255, VL-91 |
| "the v1.1 header has never been decoded by GCCMVS" | False | VL-91: `ONF001I NETWORK LOADED N=501 E=10783`, `ONF002I BIAS ROWS 9` |
| "ACC-4 fails (VL-64, VL-65)" | False | VL-112: ACC-4 PASS on the bar amended by D-340 and D-341 |
| "...and compares the full brain against Shiu, not this network" | **True** | VL-112 is measured on the 184,099-neuron brain |
| "ACC-5, ACC-6 and ACC-7 are unevaluated on it" | False | ACC-5 VL-91/VL-93; ACC-6 VL-102; ACC-7 VL-104, both on `srext` |
| "...or z/OS" | **True** | Section 8.3 row 8 is empty |

P-13 also named `prep/emit.py` as the writer. The writer is
`prep/extract.py`'s admission step, and D-269's hazard applies to it
identically: that step re-derives the subcircuit, so re-running it rewrites
`data/networks/onfnet-malecns-v1.0-srext.bin`, and IR-COM-05 puts the
network's payload CRC inside the fingerprint. One differing byte would
invalidate every Section 8.4 golden value and every MVS result taken against
them.

So the field could not be fixed by re-running its generator, and fixing it by
hand would make a generated artefact diverge from its generator, to be
silently reverted by the next generator run. That is the problem this session
had to solve, and the reason the fix is a tool rather than an edit.

## 3. Implementation approach

### 3.1 P-13: a third way between re-generating and hand-editing

`prep/netman.py` reads the manifest, sets one field of one network by dotted
path, and writes the file back in the `indent=2, sort_keys=True` spelling that
`prep/manifest.py`, `prep/emit.py` and `prep/names.py` all use. The shape is
taken from `prep/names.py`'s `register()`, which already merges a section into
this same file without regenerating a network byte, and which carries D-269's
warning inline.

D-450 named `prep/manifest.py` as the home. Reading it showed that module owns
`data/malecns/MANIFEST.json`, the FR-PRP-01 dataset retrieval manifest, a
different file that shares only a name. That was put back to the owner and
D-453 moved the amend path to a new module.

**The safety property is structural, not promised.** `prep/netman.py` imports
`argparse`, `io`, `json`, `os` and `sys`. It does not import `prep.extract`,
`prep.emit` or anything reaching a connectome, and it opens exactly one path.
It therefore *cannot* rewrite a `.bin`. Three things enforce this rather than
assert it:

1. `set_field()` requires every path segment but the last to exist already, so
   a typo in `--field` exits instead of inventing a key that reads like a real
   one.
2. `main()` compares `digest_of()` before and after the amend and refuses to
   write if any network's `bytes`, `crc32` or `sha256` moved. This cannot
   trigger by construction, which is the point: the invariant the whole design
   rests on is asserted where the write happens, not only in the test.
3. TP-10 parses the module with `ast` and fails if any forbidden module
   appears among its imports.

`prep/extract.py`'s literal was corrected in the same pass (D-454), so the
generator and the artefact now agree to the character, and TP-10 asserts that
by parsing the literal out of `prep/extract.py` without importing it. Reading
it as source matters: importing that module pulls in the whole extraction
pipeline and needs a connectome a clone does not have.

### 3.2 P-08: a row written from a measurement, not from a standing fact

`make golden` has built and run the SOFT2C golden binary on every build since
D-220. The row P-08 asked for was therefore never speculative. D-447 still
required a measurement taken in this session before the row was written,
because writing a determinism row ahead of its evidence is the failure mode
the matrix exists to prevent.

The row is numbered **3b**, not 4. D-456 made that call on a measurement:
"row 6" appears 31 times in the SRS, "row 7" 57 times and "row 8" 8 times,
plus `engine/src/onflyeng.c`, the `Makefile`, `tests/run_mvsjcc.py`,
`tests/run_mvsrun.py`, `tools/mvsjcc.py` and thirteen documents. Renumbering
would have meant 96 edits to records that are currently correct.

### 3.3 P-11: fixing an ambiguity while it costs nothing

ACC-4's shape clause said "one standard error" without saying whose.
`prep/acc4.py` had always used ONFLY's own at the earlier rate; Section 6.4
now says so (D-448).

### 3.4 P-12: retired, not applied

D-252 had already rewritten Section 9.2's Phase A row to state everything
P-12 asked for. A proposal whose content is in the document is retired, not
applied twice (D-449).

## 4. Statistical detail: why P-11 moved no verdict

ACC-4's shape clause admits a decrease between successive validation rates of
at most one standard error. Writing `m_i` for ONFLY's mean MN9 rate at
validation rate `r_i`, `sd_i` for the sample standard deviation over the
`n = 30` seeds of D-353, and `se_i = sd_i / sqrt(n)` for the standard error of
that mean, the clause as D-448 fixes it is:

> for every consecutive pair, `m_i - m_(i+1) <= se_i`

The subtraction is in that order, so a *rise* gives a negative left-hand side
and passes trivially. The candidate readings differed only in which standard
error stands on the right: `se_i` (the earlier rate, adopted), or `se_(i+1)`
(the later rate), or the Shiu reference's own.

Evaluated on `data/calibration/acc4.json`, the recorded 30-seed full-brain
campaign:

```
  rate   m_i      sd_i    se_i
    10    3.6667  4.22   0.7714
    40   14.3500  8.45   1.5425
    60   28.3833  7.85   1.4329
   120   68.3833  8.19   1.4961
   200   88.8000  5.07   0.9253

  10->40  m_i - m_i+1 = -10.6833   se_earlier 0.7714 ok   se_later 1.5425 ok
  40->60                -14.0333              1.5425 ok              1.4329 ok
  60->120               -40.0000              1.4329 ok              1.4961 ok
 120->200               -20.4167              1.4961 ok              0.9253 ok
```

Every left-hand side is negative: the dose-response curve is monotonically
increasing across all four transitions, by between 10.7 and 40.0 Hz, against
standard errors between 0.77 and 1.54 Hz. The margin is one to two orders of
magnitude, so **no candidate reading is within reach of deciding the verdict**
and the choice was free. That is the argument for making it now rather than in
the session where a dip first makes the clause load-bearing, when the reading
chosen would visibly determine a PASS.

The second clause, onset, is unaffected: ONFLY's onset (lowest validation rate
with mean above 1 Hz) is 10 Hz against the reference's 40 Hz, within one
sampled rate, and no standard error enters that comparison.

## 7. What is NOT proven

Fixed in the plan before the work (D-451) and unchanged by it.

1. **Everything here is x86-64 Windows 11 under MinGW gcc 6.3.0 and Python
   3.13.14.** No result in this session is a Linux s390x, MVS 3.8j or z/OS
   result. No MVS job was submitted, although D-445 permitted it.
2. **Row 3b is an x86 row.** It adds no MVS or z/OS coverage. ACC-5 row 7
   still covers 5 of the 19 golden requests, its `path` half having no JCC
   counterpart, and row 8 is still empty.
3. **Row 3b is a new row, not a new measurement.** This combination has run in
   every `make test` since D-220. What changed is that ACC-5's row set counts
   it.
4. **The SOFT2C agreement is evidence about ONFLY's arithmetic, not about
   GCCMVS or JCC.** Row 3b compiles the same Release 2c source rows 6 and 7
   compile, but with a different compiler on a different platform.
5. **The corrected manifest note is a documentation correction.** It restates
   VL-82, VL-91, VL-93, VL-95, VL-96, VL-102, VL-104, VL-106 and VL-112, every
   one measured in an earlier session. Nothing here re-measured any of them,
   and the note is only as true as those records are.
6. **P-11 proves nothing new about ACC-4.** It removes an ambiguity. The
   verdict, the seeds, the reference and the magnitude deviations at 10 and
   40 Hz are as VL-112 recorded them.
7. **TP-07, TP-08 and TP-09 were catalogued, not re-verified.** Their rows
   were written from each test's own docstring and the decision that allocated
   it. The tests themselves are unchanged and pass in `make test` as before.
8. **Phase F is untouched** and TBD-13, a source of a real CICS, stays open.
9. **VL-01 still applies.** Nothing here ran on real hardware.
