## 1. Problem / motivation

Every previous ONFLY result on a mainframe stops one step short of the thing
the project exists to do.

| What already ran on MVS | Where |
|---|---|
| SoftFloat 2c, TT-01/32 and TT-02 | Gate G1 (D-119) |
| A network file transported and **verified** | Gate G2 (D-141, D-150) |
| The Appendix C kernel against the oracle | `tools/mvsker.py` (D-121, D-122) |
| ONFLYDRV compiled, linked and run in MODE=REQ | Gate G4 (D-161) |

None of them is a simulation driven by a request. `tools/mvseng.py` says so at
the point where it chooses what to link:

> The kernel, the RNG and the stimulus are deliberately absent: verify-only
> never simulates, so linking them would add two job steps each to prove
> nothing.

The consequence was not merely a missing feature. **Row 6 of the SRS Section
8.3 determinism matrix — TK5 MVS 3.8j / SOFT2C / GCCMVS — had never been
filled**, and ACC-5 is defined as each golden request producing the same
fingerprint in *every* row. So ACC-5 was not a mainframe claim at all. And
**TX-01 stood PARTIAL** since Phase D closed, for the reason D-219 and VL-83
recorded: Section 8.5 defines it against MVS records and there were none to
compare.

## 3. Implementation approach

### 3.1 Two jobs, and why not one

```
ONFPREQ / ONFEREQ    ONFLYDRV, MODE=REQ, Section 8.4 control cards
                     -> HERC01.ONFLY.{P,E}REQ  (RECFM=FB,LRECL=412)
                     -> IDCAMS PRINT DUMP of what it wrote

ONFPRUN / ONFERUN    GCCMVS compiles and links 13 translation units
                     -> GO: ONFNET on the card reader, ONFREQ, ONFRSP
                     -> IDCAMS PRINT DUMP of what the engine wrote
```

That is FR-BAT-01's STEP1 and STEP2 performed for real, one job each. They are
separate because ONFREQ must exist as a **catalogued** dataset before the
engine's GO step allocates it, and because a COBOL compile deck and a C compile
deck share nothing — one job carrying both would be about 9,000 cards in which
a failure in either half stops the other.

The split also isolates the risk the owner accepted in D-260. ONFREQ is built
by ONFLYDRV rather than transported, so a defect in the driver could masquerade
as a defect in the engine. Dumping and comparing ONFREQ **before** the engine
reads it attributes such a defect at the moment it happens.

### 3.2 What the simulating link adds

`tools/mvseng.py`'s verify-only list, plus five units:

```
SF2C ONFFP2C ONFFPCC ONFFPRC ONFCRCC ONFDECC
     ONFRNDC ONFSTMC ONFKERC ONFREQC ONFCOMC      <- the five
                                     ONFI32C ONFLYENG
```

Link order is stated once, as `UNIT_MEMBERS`, and `run_deck()` asserts the
sources it builds match it. Four of the five had already been compiled on MVS
by `tools/mvssyn.py`, in this order and under these member names; only
`onfreq.c` — D-221's request loop — had never reached a mainframe.

### 3.3 ONFRSP is temporary, ONFREQ is not

ONFREQ crosses a job boundary and must be catalogued; its job deletes and
reallocates it each run, which is what makes the pair rerunnable. ONFRSP does
not cross a boundary, so it travels as `&&ONFRSP` with `DISP=(,PASS)` to the
DUMP step. A catalogued ONFRSP would need scratching first and
`mvsbld.build()` has no hook before its own SCRATCH step; a temporary dataset
needs none and cannot collide with a previous run's leftovers.

### 3.4 The signed rate column (D-265)

`CONV4` turns leading blanks into zeros and then requires four digits (D-159).
G-13 is a rate of −1, which `tools/mkreq.py` packs as a signed halfword
`FFFF`. So the **driver** answered ONF401E and the engine never saw the request
**FR-SIM-06** says it owes ONF202E. Gate G4's row in Section 9.1 had already
named this as Phase E work.

The change accepts a minus where the first non-blank character goes, replaces
it with a zero so the class test still sees four digits, and reports the fact
in `W-NUM-NEG`. The **magnitude is therefore converted by exactly the code that
converted it before** — a separate conversion path for negative numbers would
be a second place for an S0C7 to live.

Two cases needed care:

- A minus that is *not* leading (`12-0`) is already refused, because `W-LEAD`
  is `'N'` by then and the character survives into the class test.
- A minus in column 4 (`   -`) leaves no digits behind it and would otherwise
  convert to `0000` and pass. `W-NUM-SGN` records the column and the test
  refuses that one case.

The sign is honoured **at the call site, not inside `CONV4`**: the rate negates,
the duration refuses. So the duration column behaves exactly as it did before,
and the driver's division of labour with the engine is explicit — the driver
parses the *format*, the engine enforces the *range*.

## 4. Numerical details

No arithmetic changed. Two measured quantities are worth recording.

**Cost per neuron-step.** The `ONFERUN` GO step reported `CPU 13MIN 45.87SEC`
for the five `srext` requests. Each is 1000 ms at a 0.1 ms timestep, so 10,000
steps, over N = 501 neurons:

```
825.87 s / (5 x 501 x 10000)  =  825.87 / 25,050,000  =  32.97 us per neuron-step
```

That is **below** VL-41's measured band of 36.6–40.8 µs, even though this
network carries format v1.1's compensating input, which adds one binary64 add
per neuron per step (Appendix C step 1, D-190). VL-41 was taken on a synthetic
network two days before that table existed, and the two are not comparable
term by term; the number is recorded as what it is, a different measurement on
a different network.

**Where the time goes.** The whole job cost `CPU 14MIN 02.56SEC`, so the
thirteen GCCMVS compiles, the thirteen assemblies and the link together cost
**16.69 s**. On this platform the compiler is free and the simulation is
everything.

## 5. Design decisions

### 5.1 The one thing that cannot be byte-identical (D-261)

Section 8.5 defines TX-01 as "Linux s390x and MVS response records are
identical". **Taken literally that is unachievable, and always was.**

`layout/master.py` declares exactly one field of kind `'chr'`, defined in that
file as *"fixed-length alphanumeric, host code page, no translation"*:
`ONF-STIM-CODE`, bytes 0 to 7. Every other field is `'i16'`/`'i32'`,
big-endian on the wire by IR-COM-04, or `'byt'`, opaque. IR-COM-05 already
excludes text from the fingerprint with the stated reason *"so the fingerprint
is identical on ASCII and EBCDIC hosts"* — the design anticipated this for the
**fingerprint** but no requirement said how **TX-01 itself** is judged. Phase D
could not meet the question, because x86 and s390x are both ASCII.

The three candidate rules were **measured** before the owner chose:

| View | Result, all records |
|---|---|
| raw — all 412 bytes | **NO** |
| binary — bytes 8…411, no translation | **YES** |
| translated — bytes 0…7 read as EBCDIC, written as ASCII | **YES** |

D-261 chose **translated identity**. Binary-only was declined for a reason the
test suite now demonstrates rather than asserts: `run_mvsrun.py` case 17 feeds
the comparator records whose stimulus code has been replaced with `XXXXXXXX`
and requires `binary` to pass while `translated` fails. Under the rejected rule
MVS could write anything at all in that field and TX-01 would still pass.

The comparison lives in `tools/mvsrun.py` and **not** in `tests/run_tx.py`.
Phase D's comparator is byte-exact by construction, which is exactly right for
its claim — x86 against s390x, both ASCII — and weakening it to accommodate
Phase E would weaken a claim already made.

### 5.2 Additive changes to shared tools

`mvsbld.build(post=…)` and the keyword arguments on `mvscob.deck()` are both
strictly additive, and `tests/run_mvsrun.py` pins that: cases 11 and 12 require
each function's output with the new arguments defaulted to be identical to its
output without them. Copying either function was the alternative, and it is the
one `tools/mvsbld.py`'s own docstring argues against — every line of those
decks was paid for by a failure, and two copies would drift.

### 5.3 A defect caught before it reached the mainframe

`write_cards()` originally took its defaults in the signature
(`netfile=NETFILE`). Python binds that once, at import, so `select("path")`
changed **where** the card deck was written without changing **which** network
was read: `srext`'s bytes under `path`'s name. That reaches MVS and fails the
payload CRC, and FR-LOD-02's ordering would have attributed it to the
transport. Case 10b exists for it.
