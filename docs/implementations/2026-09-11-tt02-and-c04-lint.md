## 1. Problem / motivation

Two things were outstanding.

**NR-09 native-backend admission was incomplete.** Its conditions include
"passing the TestFloat vectors for the used operations", and TestFloat had never
been built or run. Until that happened, the native backend was being used on the
strength of bit-identity against the soft backend alone — which is a genuine
check, but a weaker one: two implementations sharing a systematic error would
still agree with each other.

**C-04 was an unquantified worry.** Every vendored SoftFloat external name is
far longer than the 8 characters the MVS linkage editor accepts. Nobody knew how
many, or whether they were distinguishable in their first 8 characters. "Some
names are too long" is not something Gate G1 can plan around.

## 3. Implementation approach

`tstflt.c` reads TestFloat's native vector format on stdin and compares bit
patterns, not decimal renderings — a one-ulp error is invisible in decimal. A
16-hex-digit value is parsed as two 32-bit halves, so no 64-bit integer type is
needed in the harness (NR-04) and no floating-point type appears (NR-05).

`f64_eq` is not exposed by `onf_fp`, because Appendix C never compares for
equality and offering it would widen the NR-09 admission burden for nothing. The
harness derives it as `a <= b && b <= a`, which is exactly equality for
non-NaN operands — and NaN operands are excluded anyway.

`lint_c04.py` reads external symbols with `nm`, strips the COFF leading
underscore (an ABI artifact, not part of the identifier), and reports in three
groups because the remedies differ completely: ONFLY names are defects to fix
now, SoftFloat names are a Gate G1 question, and C runtime names are PDPCLIB's
business. Only ONFLY violations fail the build.

## 4. Mathematical / numerical details

TestFloat's level-1 vectors are not random: they concentrate on the boundaries
where binary64 arithmetic actually breaks — subnormals, exponent boundaries,
values one ulp either side of a rounding tie, zeros of both signs, and
infinities. That is why 46,464 cases per operation is a far stronger check than
millions of uniformly random ones.

**Round-to-nearest-ties-to-even is requested explicitly** (`-rnear_even`), which
is what NR-01 specifies and what `softfloat/onfrpk.c` hard-wires.

Two exclusions are declared rather than silent:

- **NaN cases (VL-11, D-46).** TestFloat's reference must be built against a
  complete `softfloat.a`, and the ARM-VFPv2-defaultNaN specialization chosen in
  D-31 cannot build one because of the upstream f128 defect recorded in D-33.
  The 8086 build succeeds, and the two specializations differ *only* in NaN
  files — the arithmetic cores are shared verbatim. So NaN cases would compare a
  defaultNaN engine against an 8086 reference and report a difference that is by
  design. ONFLY aborts on any NaN before it propagates (FR-SIM-08).
- **Exception flags.** NR-10 forbids any logic depending on them and D-34
  removed the storage they would accumulate into, so the flags column is parsed
  and ignored. TT-02 proves results, not flags.

## 5. Design decisions

D-43 through D-46 are the owner's and are in Appendix A.1 with their
alternatives. One correction of my own is worth recording, because it produced a
wrong artifact before it was caught:

- **A contaminated `softfloat.a`.** An earlier failed build with
  `SPECIALIZE_TYPE=ARM-VFPv2-defaultNaN` left object files behind. The
  subsequent 8086 build treated them as up to date, producing a library that
  mixed two specializations and was missing the objects the failed build never
  compiled. It linked far enough to fail confusingly. `mingw32-make clean`
  before rebuilding fixed it: the correct library is 283,120 bytes, the
  contaminated one was 278,704. Any TT-02 result from the contaminated library
  would have been meaningless.

## 6. Verification

```
mingw32-make test
```

```
lint_nr05: 30 files scanned, 1 excluded, 0 violations
lint_c04: 41 distinct external names examined
  ONFLY     0 names longer than 8 characters
  SOFTFLOAT 13 names longer than 8 characters
run_tt02: 12 of 12 operation runs passed, 520752 cases checked,
          36816 NaN cases skipped (VL-11)
```

Per operation, both backends: `add` 43,396 checked, `sub` 43,396, `mul` 43,390,
`lt` 43,398, `le` 43,398, `eq` 43,398 — zero mismatches throughout.

### The negative control that matters most

NR-09 forbids x87 extended precision. That prohibition was tested rather than
trusted, by rebuilding the native backend **without** D-30's flags on this same
host and re-running the same vectors:

```
MISMATCH mul a=C01FFFFF:FFFFFFFF b=40800000:03FFFFFE
         got=C0B00000:03FFFFFE want=C0B00000:03FFFFFD
TT02 op=mul backend=NATIVE total=46464 checked=43390 mismatch=662
```

**662 of 43,390 multiplications are wrong**, every one off by exactly one ulp —
the double-rounding signature of x87's 80-bit registers rounding once to 64
significand bits and again to 53. On this host, `-msse2 -mfpmath=sse
-ffp-contract=off` is not a precaution; without it the native backend is simply
incorrect, and D-30 was necessary rather than cautious.

### The C-04 finding, sized

All 13 over-long SoftFloat externals share the same first 8 characters:

```
SOFTFLOA <- softfloat_addMagsF64, softfloat_countLeadingZeros32,
            softfloat_countLeadingZeros64, softfloat_countLeadingZeros8,
            softfloat_mul64To128M, softfloat_normRoundPackToF64,
            softfloat_normSubnormalF64Sig, softfloat_propagateNaNF64UI,
            softfloat_raiseFlags, softfloat_roundPackToF64,
            softfloat_shiftRightJam64, softfloat_shortShiftRightJam64,
            softfloat_subMagsF64
```

Under naive 8-character truncation these would collapse into **one** symbol. A
program that linked would call the wrong function. ONFLY's own externals are 6
to 7 characters and collide with nothing. This does not resolve the risk —
whether GCCMVS truncates, mangles or maps long names is a Gate G1 question
(A-03, R-01) — but G1 now starts with an exact list rather than a worry.

### What these results do not prove

- **x86, 32-bit mingw32 gcc 6.3.0, Windows 11 only**, on both SOFT and NATIVE
  backends. Nothing here ran under GCCMVS, JCC, MVS 3.8j, Linux s390x or QEMU;
  none is installed on this host.
- **TT-02 proves nothing about NaN behaviour** (VL-11). 36,816 NaN cases were
  excluded by design.
- **TT-01 has not been run.** The 64-bit integer self-test is what actually
  de-risks assumption A-05 on GCCMVS, and it would prove nothing on this host,
  where 64-bit arithmetic already works. Gate G1 still needs it.
- NR-09 admission is now satisfied **on this host**: SSE2 with contraction off,
  TestFloat vectors passing, and byte-identical golden fingerprints against the
  soft backend. It says nothing about any other host, and VL-01 still applies to
  QEMU when Phase D arrives.
- The C-04 lint reports; it does not fix. No SoftFloat name was shortened.
