## 1. Problem and motivation

ACC-5 is satisfied only when every golden-suite request yields the same
fingerprint on every combination Section 8.3 lists. Row 7, TK5 / SOFT2C /
**JCC**, was filled on 2026-09-15 by D-281 to D-286 and VL-93, but only for
`srext`: five of the nineteen Section 8.4 requests.

Row 7 exists to answer a question no other row can ask. Everything the engine
does is integer work over a software float library, so a code-generation
difference would not surface as a rounding difference; it would surface as a
wrong answer, or not at all. Rows 6 and 7 are the same machine, the same
backend and the same thirteen translation units through two different code
generators, and they are the only pair that can separate "this fingerprint is
a property of ONFLY's source" from "this fingerprint is a property of
GCCMVS".

Until this session that pair covered five requests on a 501-neuron network,
and in particular it covered **none of the three rejection paths**. G-11
(ONF201W, reserved stimulus), G-12 (ONF203E, unknown stimulus) and G-13
(ONF202E, out-of-range rate) are all `path` requests. Row 6 reached them on
2026-09-15 and its implementation doc called that "the first time the MVS
engine has reached FR-BAT-05's, D-41's and FR-SIM-06's rejection paths".
Under JCC they had never been reached at all.

With every phase through G complete (D-442) and Phase F blocked on the IBM Z
access request, which has not been granted, this was the largest named coverage
gap that could be closed rather than started (D-458).

## 3. Implementation approach

### 3.1 The refusal became an assertion

`tools/mvsjcc.py` refused `--net` outright, and the refusal named the failure
it was guarding: *the wrong network under the right job name*. That is the
worst failure this tool can have, because the evidence of which network a run
read is exactly the thing that has gone wrong, and the cost of discovering it
is hours of TK5. `tools/mvsrun.py` records the same class of bug biting twice
in one session through mutable-looking default arguments.

The fix is not to delete the guard but to remove the failure mode it guarded
and then assert the absence:

1. **Each network carries its own names** (D-462). `srext` keeps `ONFJRUN`
   and `HERC01.ONFLY.JRSP`, exactly as VL-93 recorded them; `path` takes
   `ONFJPRUN` and `HERC01.ONFLY.JPRSP`. A listing on disk is written under
   its job's name, so the file says which half produced it.
2. **`jcc_job()` and `jcc_rsp_dsn()` resolve on every call**, never bound at
   import, because a module global captured once is precisely how half the
   names follow `select()` and the other half do not.
3. **`check_names()` runs before any deck is built.** It refuses a network it
   has no names for, refuses a `mvsrun` whose `NET_DSN` and `REQ_DSN`
   disagree with its own `NETNAME` (which is what a caller setting the
   globals by hand would produce), and refuses any response dataset that
   collides with row 6's, because row 6's records are the comparand row 7 is
   judged against and a run that overwrote one would destroy its own
   evidence.

`tests/run_mvsjcc.py` proves `check_names()` **refuses**, not merely that it
exists. A guard that cannot fail is not a guard.

### 3.2 The timeout, sized from two measurements rather than one

The collector waited 7200 s, which was ample while row 7 was `srext` only.
Row 6 ran the identical fourteen `path` requests **twice**, and the pair is
the honest estimate:

| Run | Job | Wall | `GO` step CPU |
|---|---|---|---|
| The run VL-91 reports | JOB 279 | 05:57:26 to 07:01:11 | 63 min 04.79 s |
| The listing committed at `891de23` | JOB 308 | 14:15:46 to 16:59:38 | 157 min 52.69 s |

JCC's code costs 0.874 of GCCMVS's on the identical `srext` work (15 min
29.88 s against 17 min 43.33 s of `GO` CPU), so the honest upper bound was
over two hours of `GO` alone. `RUN_TIMEOUT` is 14400 s. The cost of getting
this wrong is not a retry: `collect()` returns `None` and the listing is lost
*after* the CPU has been spent.

### 3.3 `--recover`, because the job outlives its submitter

`tools/mvsrun.py::recover` had anticipated this in its own docstring before
it happened. `tools/mvsjcc.py` had no equivalent, and the process submitting
ONFJPRUN ran under a ten-minute cap against a job of hours. D-465 ports the
mechanism: read the printer, take the **last** complete JES2 START/END pair
for the job, and hand it to the same `process_run()` that `--run` uses. The
last pair and not the first, because a job name that has run before appears
in the printer more than once.

## 4. Design decisions

| Decision | Alternative | Why |
|---|---|---|
| D-462, per-network job and dataset names | One job name and one dataset, scratched between runs | The printer and punch hold every run. Distinct names are what lets a figure be recovered later by naming its job rather than by re-running TK5 |
| D-464, extend `tests/run_mvsjcc.py` | A new `tests/test_mvsjcc.py` under the `prep` target, as D-461 worded it | The approved wording was false on disk: `run_mvsjcc.py` already existed with its own Makefile target. The engineer reported it and the owner ruled, rather than the engineer deciding |
| D-465, add `--recover` | Leave the tool as planned | Without it, a killed submitter costs another one-to-three-hour TK5 run |
| D-463, amend VL-91 | Leave it, or note it only in VL-138 | VL-91's 63-minute figure is checkable against a committed listing that says 157. An auditor would read the SRS as wrong; it is not, it named a run whose listing was later overwritten |
