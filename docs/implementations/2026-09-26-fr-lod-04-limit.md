## 1. Problem / motivation

FR-LOD-04 says ONFLYENG "shall fail with ONF105E before allocation if it
exceeds the configured limit". The decoder has implemented the check since
Phase B, and `tests/run_dec.py` and `tests/run_syn.py` exercise it, but the
program itself called `onfdec(buf, len, 0, &net, &need)`: a limit of 0, "no
limit", everywhere. The comment gave TBD-14 as the reason, yet D-116 had
closed TBD-14 at 8M on 2026-09-11. So no ONFLYENG build on any platform could
emit ONF105E, and `tests/run_eng.py`'s replay of TE-08 through the program had
to skip, which D-548 turned into a standing exemption.

On MVS 3.8j, where C-01 gives a region of single-digit megabytes, the
consequence of a network too large for the region was an allocation failure
or an abend rather than the clean ONF105E refusal NFR-REL-01 asks for.

The survey for the plan found a second, related defect: `ONF_MAXPAY`, the
sanity bound on a declared payload length, keyed its MVS branch on `__MVS__`
or `__CMS__`. JCC predefines neither (D-291), so a JCC build printed
`PLATFORM MVS38J` while using a development host's 512 MB bound rather than
D-147's 64 MB (P-45 S5).

## 3. Implementation approach

**One platform test, made once.** `onfplat.h` already decides the platform
once, for the manifest's `ONF_PLATID`. The two branches that name `MVS38J`
(the `__MVS__`/`__CMS__` branch and the JCC branch, which follows `__s390x__`
and `_WIN32` in the chain by D-291) now also define `ONF_ISMVS`. Both
machine-dependent sizes key on that flag and nothing else, so neither can
disagree with the platform the manifest prints. That is the defect S5 found
in `ONF_MAXPAY`, closed by construction rather than by a second, parallel
test.

**The limit.** `ONF_MEMLIM` is defined inside `#ifndef ONF_MEMLIM`: 8388608L
where `ONF_ISMVS` is set and `0` elsewhere. The `0` is spelled as the literal
the call used to carry, so wherever the limit is 0 the preprocessed
`onflyeng.c` is the text it was before. ONFLYENG passes the macro to `onfdec`,
whose contract is unchanged: it computes the requirement from the header
counts after FR-LOD-02's declared-length check and before the payload CRC,
and returns ONFD_MEM (ONF105E, return code 12) when a positive limit is
exceeded. No allocation happens before that return.

**TE-08 through the program.** Because the limit is a build constant, the
whole-program test cannot vary it at run time. The `eng` target therefore
builds ONFLYENG twice more per backend with `-DONF_MEMLIM` at
`tests/run_dec.py`'s two TE-08 limits (64 and 1,048,576), linked exactly as
the shipped build, and `run_eng.py` replays each TE-08 case on the build made
at that case's limit. A case with no matching build fails; it is never
skipped, because a quietly dropped case is how the check went unrun from
D-78 to D-564.

**The shipped limit, on each side.** Off MVS, `run_eng.py` feeds the shipped
build a network whose header demands 8,388,616 bytes and expects ONF003I:
the MVS limit has not leaked. On MVS, `tools/mvsrun.py --te08` sends the
same bytes through the card reader to the GCCMVS-built ONFLYENG and expects
ONF105E at COND CODE 0012, after a first step that verifies the installed
`srext` network and must end at 0000. The same file is admitted on one
platform and refused on the other, which is what D-568 says should happen.

**The over-limit network.** `overlimit_network()` takes the 16-neuron sample
network every TE case uses, raises the header's edge count until the
requirement exceeds the limit, and reseals the header CRC. The payload is
untouched, so checks 1 to 5 of FR-LOD-02 pass and the memory gate is the
first check that can refuse the file; where no limit applies, verify-only
mode never reaches `onfldp`, the only code that reads the inflated count, so
the file verifies.

Contracts of the new helpers (`tests/run_dec.py`): `need_bytes(data)` takes
network bytes and returns FR-LOD-04's requirement in bytes, read from the
header only, with no side effects. `overlimit_network(good, limit)` returns
new bytes, `good` itself if it already exceeds `limit`; it never modifies its
argument.

## 4. Mathematical / numerical details

FR-LOD-04's requirement, as `onfdec` computes it from the header (n neurons,
e edges, D delay steps, b compensating-input rows), in bytes:

    need = 4(n + 1) + 12e + 16n + 8Dn + 16n + 4b + 8bn

that is: row pointers; a 4-byte target and an 8-byte weight per edge; u and g
per neuron; the delay ring; four int32 arrays per neuron; the table's rates
and rows. The engine accumulates it in 64 bits and refuses anything that
overflows a signed 32-bit count (NR-11).

For the four networks, from their verified headers: `srext` (n 501, e 10,783,
D 18, b 9) needs 255,688; `path` (913, 72,852, 18, 9) needs 1,104,340;
`hop2` needs 23,859,952; `full` (184,099, 24,775,486, 18, 0) needs
330,443,656.

The over-limit network: the sample network needs 3,856 bytes. Each added
edge adds 12, so reaching L + 1 = 8,388,609 needs
ceil((8,388,609 - 3,856) / 12) = 698,730 more edges, which gives
3,856 + 12 x 698,730 = 8,388,616 bytes: 8 bytes over the MVS limit, the
closest a 12-byte step allows. An MVS build whose limit were anywhere from
8,388,616 up would admit it, so its refusal shows the limit is at most
8,388,615; admitting `srext` shows it is at least 255,688. The MVS run
bounds the limit to that interval, which 8,388,608 lies in; it does not
measure the value itself, which the preprocessor check does on x86.

## 5. Design decisions

- **Build-time constant, not a PARM keyword** (D-567, the owner's choice).
  A PARM keyword would have needed a combined grammar and amendments to
  IR-STM-01 and ONF908S; the constant changes no requirement text.
- **8M on MVS 3.8j, none elsewhere** (D-568). CMS shares the MVS branch, as it
  has since D-147 for `ONF_MAXPAY` and for `ONF_PLATID`; no ONFLY build has
  targeted CMS. That grouping follows the header's existing platform
  identification and was not put to the owner separately.
- **Visible only through ONF105E** (D-569): no manifest line, so no recorded
  SYSPRINT gains one.
- **`ONF_MAXPAY` fixed in scope** (D-572), through the same flag.
- **`ONF_ENGVER` bumped to 0.5.1** (D-573), against the engineer's
  recommendation. As a result every ONFLYENG object changes in one byte, and
  the first tag D-544 fixed at `v0.5.0` no longer matches the version this
  engine prints; that question is open for the owner before slice G.
- **Architect's choices within the approved plan:** the flag's name
  `ONF_ISMVS`; the helper's home in `tests/run_dec.py`, which
  `tools/gensyn.py` already imports; GO before GO2 in the MVS job, so that
  GO2's ordinary `COND=(4,LT)` is the right condition; and the build names
  `onflyengl` and `onflyengm` for the two limit builds.
